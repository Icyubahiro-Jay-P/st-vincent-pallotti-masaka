## 1. Code of Conduct

This project adheres to a Code of Conduct. By participating, you agree to uphold it. See [CODE_OF_CONDUCT.md](./CODE_OF_CONDUCT.md) for details.

## 2. How Can I Contribute

Ways to contribute include:

* Reporting bugs and suggesting enhancements via GitHub Issues
* Improving documentation, translations, and accessibility
* Fixing bugs, improving performance, and adding features
* Reviewing pull requests and testing changes
* Improving design, content accuracy, and SEO

If you plan a large change, please open an issue first to discuss the approach before investing significant time.

## 3. Development Setup

### Prerequisites

* Node.js 20 or later (Node 22 recommended)
* npm 10 or later
* A Neon Postgres database or any Postgres compatible database for Drizzle ORM
* Git

### Steps

1. Fork the repository and clone your fork:

   ```bash
   git clone https://github.com/YOUR_USERNAME/st-vincent-pallotti-masaka.git
   cd st-vincent-pallotti-masaka
   ```

2. Install dependencies:

   ```bash
   npm install
   ```

3. Configure environment variables:

   Create `.env.local` in the project root. At minimum you will need:

   ```
   DATABASE_URL=postgresql://user:password@host/db?sslmode=require
   BETTER_AUTH_SECRET=your-random-secret-at-least-32-chars
   BETTER_AUTH_URL=http://localhost:3000
   RESEND_API_KEY=re_xxx
   CLOUDINARY_CLOUD_NAME=xxx
   CLOUDINARY_API_KEY=xxx
   CLOUDINARY_API_SECRET=xxx
   DEEPL_API_KEY=xxx
   ```

   Refer to `.env` and `drizzle.config.ts` for the full list of expected variables. Never commit `.env` or `.env.local`.

4. Prepare the database:

   ```bash
   npm run db:generate
   npm run db:migrate
   npm run seed:admin
   npm run seed:programs
   npm run seed:milestones
   npm run seed:site-settings
   npm run seed:values
   npm run seed:homepage-content
   ```

5. Start the development server:

   ```bash
   npm run dev
   ```

   Open http://localhost:3000 in your browser.

### Useful Scripts

```bash
npm run dev              # Start Next.js with Turbopack
```

## 5. Branching and Commit Guidelines

* Create a feature branch from `main`:

  ```bash
  git checkout -b feat/short-description
  git checkout -b fix/short-description
  git checkout -b docs/short-description
  ```

* Use clear, conventional commit messages when possible:

  ```
  feat: add Kinyarwanda dictionary
  fix: correct admissions form validation for phone numbers
  docs: clarify environment setup in README
  chore: update dependencies
  ```

* Keep commits focused and atomic. One logical change per commit.
* Rebase or pull with rebase before opening a pull request to avoid unnecessary merge commits.

## 6. Pull Request Process

1. Ensure your branch is up to date with `main`.
2. Run checks locally before pushing:

   ```bash
   npm run lint
   npm run typecheck
   npm run build
   ```

3. Push your branch and open a pull request against `main`.
4. Fill in the pull request template if present. Describe what changed, why, and how you tested it. Include screenshots for UI changes.
5. Link any related issues using `Closes #123` or `Fixes #123`.
6. Be responsive to review feedback. A maintainer will review as soon as possible.
7. All checks must pass and at least one approval is required before merging.
8. Squash or rebase merging is preferred to keep history clean.

## 7. Coding Standards

* **TypeScript:** Strict mode is enabled. Avoid `any`. Prefer explicit types for exported functions.
* **Formatting:** Prettier is configured with `prettier-plugin-tailwindcss`. Run `npm run format` before committing. ESLint must pass.
* **Styling:** Tailwind CSS v4 and shadcn/ui. Use design tokens from `app/globals.css` and utility classes from `lib/utils.ts`.
* **Accessibility:** Use semantic HTML, proper heading hierarchy, alt text for images, and keyboard accessible interactions. Test with keyboard navigation.
* **Performance:** Prefer Next.js Server Components where possible. Keep client components small and focused.
* **Security:** Never commit secrets. Validate all user input with Zod schemas in `lib/validations`. Sanitize rendered user content.

## 8. Internationalization (i18n)

All user facing copy lives in `lib/i18n/dictionaries/en.ts` and `lib/i18n/dictionaries/fr.ts`. English is the source of truth for shape.

* When adding or renaming a key, update both dictionaries. TypeScript will error if `fr.ts` is missing a key.
* To add a new language, for example Kinyarwanda:

  1. Copy `lib/i18n/dictionaries/fr.ts` to `lib/i18n/dictionaries/rw.ts` and translate values, keeping keys identical.
  2. Add `"rw"` to the `locales` array and `localeNames` in `lib/i18n/config.ts`.
  3. Register the dictionary in `lib/i18n/get-dictionary.ts`.

* Language is stored in a cookie, not in the URL. Do not add locale prefixes to routes.
* If you use an auto translation helper such as DeepL, always have a native speaker review the output before merging.

## 9. Database and Seeds

* Schema is defined with Drizzle ORM. After changing schema files, run `npm run db:generate` to create a migration and `npm run db:migrate` to apply it.
* Seed scripts in `scripts/` populate reference data. Run only the seeds you need and avoid running seeds twice without checking for duplicates.
* Do not edit generated files in `drizzle/` by hand.
* For database problems, run `npm run check:db` to verify connectivity.

## 10. Reporting Issues

* Use the GitHub Issues tab. Search existing issues before opening a new one.
* For bug reports, include: expected behavior, actual behavior, steps to reproduce, browser and OS, and screenshots or logs if relevant.
* For feature requests, describe the problem you want to solve and the proposed solution. Include alternatives you considered.

## Questions

If you have questions that do not fit an issue, open a discussion or contact the maintainers through the repository. Thank you for helping make this project better for the Pallotti Masaka community.
